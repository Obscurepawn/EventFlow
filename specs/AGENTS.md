# 规格与证据协作约定

本目录继承[根约定](../AGENTS.md)。开始工作先读 [INDEX](INDEX.md)及相关规格，再核对源码、测试和工作树；规格记录授权目标，源码与 fresh evidence 说明实现状态，两者不能互相替代。

## 状态与范围

- `core-delivery.md` 和其 verification 记录描述已验收核心快照；`product-scope.md` 保留完整产品范围及后置项。后续重构须单独维护状态和新证据，不能覆盖历史结论来制造完成状态。
- 同一规格包含历史提案和后续决定时，读到最新授权与实施记录。当前 `trigger-api-ergonomics.md` 文末已经扩大到 typed Pattern、静态 Function、capture 与 session；不要用前文“仅建议”否定该授权，也不要据此扩大为动态 UDF 家族或 Process Function。
- 用户已授权的文档初始化等维护任务可建立轻量记录，不改变其他 active 任务的 owner、验收门槛或状态。
- 在有意义的状态变化和交接前更新目标/范围、owner、任务状态、决策、Changed files、验证、剩余缺口和下一步。新 spec 加入 INDEX，结束时同步状态；不要只依赖聊天记录。

## 审查与验证

- `reviews/` 保存独立审查原发现和实施者处置；每份报告注明检查范围、实际证据、未验证项。保留问题到修复的对应关系，不删除失败记录或把实施者自查称作独立审查。
- 每个完成的 milestone 按根约定执行一次 fresh-context 独立审查；最终产品交付由多位独立 reviewer 在同一轮并行全局检查要求、架构/接口、实现和测试证据。整改后定向复验，不自动重复发起轮次或每组件各开一轮。
- 对协作说明等文档维护，审查范围为本次授权及修改内容，不重新宣布产品 milestone 或未运行的系统质量门禁通过。
- `verification/` 中的日志、源码 hash 和二进制证据必须绑定实际检查对象、命令及结果。检查命令清单、计划执行或历史绿灯都不是当前通过证据。
- 不提交密钥、私有 PDF、聊天转储或新增长篇原始日志；正文保留必要摘要和有用的本地证据路径。
- `archive/` 仅供历史追溯，不从旧提案覆盖当前合同。引用旧文件时先查 [archive 索引](archive/README.md)中的迁移映射。

提交文档前检查改动中的链接、围栏和状态一致性；只有验收项、实际修改与验证相符才标记完成。未执行的构建、真实 broker 或恢复探针必须如实保留为未验证。
